# Controlled e-GP Execution Location Enrichment — R2B Design

Status: Human-approved design sections 1, 2 and 3-R1; documentation only.
Implementation is gated by the M0 real-response proof in this document.

## 1. Problem and goal

The real TBMT source TBMT_3_9_2026.xlsx currently contains 174 opportunities
and has execution-location coverage of 0/174. Bid Radar truthfully renders a
missing execution location as UNKNOWN / — and disables location filtering when
coverage is zero.

R2B adds a controlled, source-backed enrichment path. It must not mutate the
workbook observation, weaken provenance, infer a location from unrelated
business fields, or silently turn a technical failure into NO_MATCH.
Import remains local and deterministic; network enrichment is a separate,
explicit Human action.

## 2. Evidence and limits from SPIKE-EGP-EXECUTION-LOCATION-01

The spike established:

- The public e-GP detail page is an HTML/Vue shell.
- The detail/search flow uses reCAPTCHA at runtime; no login requirement was
  proven.
- Tokenless detail/search replay returned HTTP 400.
- The public version-list resolves revision UUIDs.
- Exact revision UUIDs differ for revisions 00 and 01 of IB2600488839.
- The frontend assigns response.data to this.tbmt; this does not prove that
  the raw response has a top-level tbmt key.
- The frontend references bidpBidLocationList and lsBidpBidLocationDTO as
  location-list candidates.
- Actual semantic location values were not captured during the spike.
- CAPTCHA or access-control bypass is forbidden.

These observations establish a browser-session design constraint, not
permission to call e-GP during this documentation work.

## 3. Approved architecture and ownership boundaries

The flow is:

    GUI
      -> thin GUI service adapter
      -> Execution Location Enrichment application service
      -> EGP Browser Detail Provider
      -> existing BrowserFetcher / Playwright context
      -> normal official e-GP frontend requests
      -> observed official response and provenance
      -> pure structured-location parser
      -> enrichment evidence projection
      -> Bid Radar

The GUI does not call Playwright, parse raw JSON, or own enrichment policy.
gui_services.py remains an adapter. The application service owns identity,
cache lookup, queueing, progress and outcome classification. The provider owns
official navigation, UUID resolution, response observation and raw provenance.
The parser is pure and has no network, filesystem or GUI dependency. The cache
stores evidence, not application authority.

tbmt_importer remains local-only and filter_engine remains network-free. The
crawler must never export a reCAPTCHA token for HTTP replay.

## 4. Human trigger and browser policy

Enrichment is never automatic on workbook import. The only R2B trigger is the
explicit Human action BỔ SUNG ĐỊA ĐIỂM TỪ e-GP.

The provider may use the official frontend through the existing BrowserFetcher:
normal navigation/search and observation of responses generated by that
frontend are allowed. Token extraction, token export, HTTP replay with a
harvested token, challenge solving, proxy rotation and fingerprint spoofing
are prohibited. The existing domain policy, robots check, Playwright context
and rate-limiting seam are reused; no second browser stack is introduced.

The presence of a reCAPTCHA script alone is not a challenge. A challenge
requires visible verification UI, an explicit challenge/block response, or a
governed AccessPolicy block decision. On a real challenge, stop the whole
batch, preserve completed validated evidence, leave unprocessed items as
NOT_PROCESSED, and show the Human that e-GP access verification stopped the
batch. There is no bypass control.

## 5. Exact identity vocabulary and binding

Use these distinct values:

    official_notify_no = IB2600488839
    revision           = 00
    source_revision_id = IB2600488839-00
    notify_id          = UUID-A

OpportunityIdentity.base_id corresponds to the official notify number,
OpportunityIdentity.revision is the revision, and raw_id may represent the
source revision id. notifyNo must not be written as IB2600488839-00; the
official version response separates notify number and version.

Every acquisition binds requested identity, resolved e-GP identity and the
observed request/response. A response with the wrong revision or UUID is
INTEGRITY_MISMATCH, is rejected, and stops the batch. If the response does not
echo identity, causal binding is still proven by the exact revision lookup,
the resolved UUID request and the response observed for that request.

Revision 00 and revision 01 are independent jobs and evidence. Evidence from
one revision is never reused for the other without that revision's own proof.

## 6. M0 real-response proof gate

No production parser, cache, provider, orchestration or UI implementation may
start until M0 captures one to three official browser-native detail responses
containing real semantic location values.

M0 must prove:

1. the actual response envelope;
2. the actual detail-object path;
3. the exact revision and UUID binding;
4. the relationship of official notify number, revision and UUID;
5. the actual location DTO path;
6. at least one real, meaningful execution-location component and preservation
   of whichever province, district and ward fields the source supplies.

Because the R2B MVP exposes a province/city filter, M0 must additionally prove
at least one official detail response with an explicit usable province/city
value. A district or ward without an explicitly evidenced province/city proves
only partial-location parsing and does not authorize province/city-filter
implementation. M0 therefore requires M0_REAL_PROVINCE_CITY_VALUE = PROVEN
before that filter is implemented. Missing components remain unconfirmed.

The frontend variable name tbmt is not sufficient proof of a raw JSON envelope.
If M0 cannot prove these facts, stop for Planner and do not ship production
parser/cache/UI code.

## 7. Structured execution-location contract and filter level

One DTO is one structured administrative evidence record with province,
district, ward, source path and evidence provenance. Province, district and
ward are components of one location, not three separate locations. Components
may be independently present or absent.

The R2B MVP filter contract is:

    R2B_LOCATION_FILTER_LEVEL = PROVINCE_CITY_ONLY

The Bid Radar Địa điểm thực hiện selector contains only source-confirmed
province/city values. For example, province Đồng Nai with district Long Thành
and ward Long Phước contributes only Đồng Nai to the province/city selector.
District and ward remain structured detail evidence and are not filter options.

Semantic location quality is separate from acquisition outcome:

    CONFIRMED = province/city is explicitly supported by the same opportunity's
                 supported source evidence.
    PARTIAL    = usable district and/or ward exists, but province/city is not
                 explicitly confirmed.
    UNKNOWN    = no usable execution-location evidence exists.

These quality labels do not replace RETRIEVAL_FAILED, SCHEMA_UNSUPPORTED,
ACCESS_CHALLENGE or INTEGRITY_MISMATCH.

Authority precedence is:

1. explicit execution-location fields in the workbook source observation;
2. supported structured e-GP execution-location evidence;
3. UNKNOWN.

District or ward must never be used to infer a parent province/city:

    DISTRICT_WARD_TO_PROVINCE_INFERENCE = FORBIDDEN

If the source says district Bình Chánh and provName is absent, preserve district
Bình Chánh and set province/city to UNCONFIRMED. Do not infer TP. Hồ Chí Minh.
If the source explicitly supplies district Đông Anh and provName Hà Nội, Hà Nội
is confirmed. No static district-to-province table, geocoder, general
geographic knowledge, package/project name, procuring entity address, investor
address, issueLocation or receiveLocation may fill a missing parent.

The same-evidence rule applies to workbook data. An explicit workbook value
such as Thành phố Hà Nội or Huyện Đông Anh, Thành phố Hà Nội may confirm Hà Nội.
A workbook observation containing only Huyện Đông Anh cannot acquire a parent
city from general knowledge. R2B adds no geographic normalization capability.

The parser keeps the collection and source paths; UI display may render a
friendly joined string, but filtering consumes structured evidence. A joined
display string is never reparsed as authority.

## 8. Immutable source and effective projection

OpportunityRadarItem remains the immutable workbook/source observation. Live
enrichment must not be injected into source_fields, raw_fields,
location_detail_raw, or any provenance-bearing workbook field.

The application layer owns an ExecutionLocationEvidenceIndex and an
EffectiveOpportunityProjection. GUI and filter evaluation read the same
effective projection, while workbook SHA, sheet, row and source coordinates
remain unchanged.

## 9. Cache design and integrity

R2B uses an L1 session cache and an L2 persistent filesystem raw-evidence
cache, with no DB migration.

The lookup key is exactly source_type + base_id + revision, for example
TBMT / IB2600488839 / 00. A UUID is not required before this cache lookup;
notify_id is evidence metadata, not a lookup key. Cache metadata includes
official notify number, source-revision id, revision, notify id, retrieval
timestamp, raw SHA-256, raw-schema version, parser-contract version and
retrieval method.

On read, verify manifest identity, recompute raw SHA-256 and check compatible
parser/schema versions. A modified raw file is CACHE_CORRUPT and is rejected.
On write, write a temporary file, verify it, and atomically replace the target.
Never store reCAPTCHA tokens, cookies, Authorization headers or browser
secrets. The cache is a source snapshot, not live truth. Invalidate on hash or
identity conflict, unsupported parser/schema version, or explicit Human
refresh; no arbitrary TTL is required for the MVP.

## 10. Item and batch outcomes

An item may end in FOUND, SOURCE_HAS_NO_LOCATION, RETRIEVAL_FAILED,
SCHEMA_UNSUPPORTED, INTEGRITY_MISMATCH, ACCESS_CHALLENGE or NOT_PROCESSED.

FOUND requires correct identity, supported detail schema, at least one valid
DTO and at least one meaningful non-empty location component. An all-empty DTO
is not FOUND. A province-only record may be FOUND and CONFIRMED for the
province filter; a district-only record may be FOUND with PARTIAL quality and
must remain UNKNOWN for province filtering.

SOURCE_HAS_NO_LOCATION is valid only after identity, supported detail schema
and supported location structure are confirmed and the source contains no
usable meaningful component. It is not a synonym for malformed payload,
schema change, wrong revision, wrong UUID or retrieval failure.

Malformed or unknown payloads are SCHEMA_UNSUPPORTED; wrong revision/UUID is
INTEGRITY_MISMATCH.

Batch outcomes are COMPLETED, PARTIAL, STOPPED_ACCESS_CHALLENGE,
STOPPED_INTEGRITY_MISMATCH, CANCELLED_BY_HUMAN and FAILED_BEFORE_START. An
integrity mismatch is safety critical: reject the evidence, stop scheduling
further acquisition jobs and set STOPPED_INTEGRITY_MISMATCH.

Technical absence remains location criterion = UNKNOWN. PARTIAL evidence is
preserved and visible but does not populate the province/city selector, does
not match a province solely by inference, and yields UNKNOWN for an active
province/city criterion. Never convert RETRIEVAL_FAILED, SCHEMA_UNSUPPORTED,
ACCESS_CHALLENGE, INTEGRITY_MISMATCH or NOT_PROCESSED to NO_MATCH.

## 11. Queue, rate limit and cancellation

The queue contains exact identity jobs, not only base ids. Concurrency is one.
The existing 12 requests/minute setting means the maximum Crawler-initiated
detail acquisition attempts per domain. It does not claim to limit every
browser asset or API request. Retries consume the same acquisition budget.

The DỪNG action stops scheduling new items, makes retry/rate-limit waits
cancellable, and gives the active acquisition a finite governed timeout. The
current page/browser is closed safely; only fully validated evidence is
preserved; the batch becomes CANCELLED_BY_HUMAN. There is no infinite wait or
browser kill during an evidence write.

## 12. Source and UI freshness

Each batch records source type, resolved source path, source SHA-256, a
generation id and requested observation keys. Results may be persisted to the
cache, but are applied to Bid Radar only if the current active-source
fingerprint is identical. A workbook change produces STALE_BATCH_RESULT and
prevents stale application.

During enrichment the UI shows progress only. On completion, Human cancel,
challenge stop or integrity stop, apply accumulated valid evidence once,
refresh coverage, rebuild location options and rerun the active Radar
evaluation once when necessary. Province/city coverage counts only records
with CONFIRMED province/city authority. For example, 120 confirmed,
15 district/ward-only PARTIAL and 39 UNKNOWN records yield province-filter
coverage 120/174, not 135/174. UI may say Tỉnh/Thành phố đã xác nhận: 120 / 174
gói. Partial detail remains inspectable in the Inspector, for example
Địa điểm nguồn: Bình Chánh; Tỉnh/Thành phố: Chưa xác nhận.

A valid selected province/city is preserved. If it is no longer present, emit
FILTER_SELECTION_INVALIDATED with a visible notice; do not silently reset to
Tất cả. A genuine source switch may reset source-derived selection.

## 13. Workbook immutability and multi-location display

The input workbook is read-only. Its SHA-256 before enrichment must equal its
SHA-256 after enrichment. Enriched evidence exists only in the evidence cache
and current Radar projection.

Multiple DTOs remain a collection of structured records. A display may join
their values, but the joined string is not a new geographic authority.
Filtering passes when any structured execution-location evidence satisfies the
selected value.

## 14. Planned decomposition

R2B is staged rather than one large commit:

    R2B-M0  real browser response validation
    R2B-M1  structured execution-location contract and pure parser
    R2B-M2  exact-revision filesystem evidence cache
    R2B-M3  browser-native e-GP detail provider
    R2B-M4  effective projection and batch orchestration
    R2B-M5  explicit Bid Radar enrichment UX
    R2B-M6  real-source acceptance and regression

M1 through M6 remain held behind the M0 gate.

## 15. Required acceptance-test contract

Parser and source authority tests cover one primary DTO, multiple DTOs,
supported fallback, a supported schema with no usable location, an all-empty
DTO, issue/procuring-address-only payloads, malformed/unknown payloads and
workbook explicit location outranking live evidence. They also cover explicit
province/city filter authority, district-only PARTIAL evidence, ward/district
without parent inference, confirmed/partial/unknown coverage, Inspector
partial display and the rule that joined display text is never reparsed.

Identity and cache tests cover independent revision 00/UUID-A and
revision 01/UUID-B, wrong response revision or UUID as INTEGRITY_MISMATCH,
zero browser calls on cache hit, browser/raw/SHA on cache miss, revision
mismatch as miss, modified raw rejection and atomic writes.

Projection, freshness and UI tests cover immutable provenance, GUI/filter use
of one effective projection, stale-source rejection, selected-location
preservation and Human-visible invalidation.

Batch tests cover prior successes surviving a challenge, pending items as
NOT_PROCESSED, bounded transient retry, no CAPTCHA retry as an ordinary
timeout, finite cancellation during retry/rate-limit wait, and
INTEGRITY_MISMATCH producing STOPPED_INTEGRITY_MISMATCH with no further jobs.

The explicit province/city acceptance set includes: province Đồng Nai with no
district still filters Đồng Nai; district Bình Chánh with no province remains
PARTIAL, visible and UNKNOWN for province filtering; no administrative parent
is inferred; only confirmed province/city records increase coverage; and M0
must provide one real explicit province/city value before province-filter
implementation is authorized.

Real-source acceptance verifies an exact revision, a real semantic location,
the displayed value, corresponding filter behavior and workbook hash equality.
Coverage greater than zero is only a smoke signal, not final acceptance.

## 16. Acceptance boundaries and non-goals

R2B does not mutate the existing immutable workbook/source observation
contract, add a database schema migration, write back to XLSX, infer
province/city from names or addresses, solve CAPTCHA, export tokens, create a
second browser stack, or authorize automatic enrichment. Future implementation
may add bounded application-layer value objects such as
ExecutionLocationEvidence, ExecutionLocationEvidenceIndex and
EffectiveOpportunityProjection, provided OpportunityRadarItem source
provenance remains immutable.
There is no scheduler, daemon, MCP connector, auto-Spine, auto-merge or
auto-release behavior.

The R2B design is accepted for specification review only. A Reviewer PASS,
machine evidence or a cache-integrity PASS does not authorize Human release,
merge or the next Micro-WP.
